# Qvorum

Qvorum is a management platform for apartment buildings and homeowners' associations. It replaces the chat groups that building administrators usually rely on with one place for announcements, maintenance bills, online payments, meter readings, repair requests and votes.

The user interface, the code and the documentation are in English.

## Applications

| Application | Users | Main features |
| --- | --- | --- |
| **Mobile app** (`mobile/`) | Residents | digital notice board with read confirmation, in-app notifications, meter readings with photo, number of occupants, maintenance bill, payment history and receipts with CSV export, online payment (Stripe), votes, issue reports with status tracking |
| **Web app** (`web/`) | Building administrator, association president | administrator registration together with the association, apartments and meters, user accounts (residents and the president) with temporary passwords, announcements, votes and results, invoices and maintenance bill generation, issue reports sent to service companies, administrative deadline calendar, arrears, penalties and cash payments, statistics, CSV export; the president approves expenses above a threshold and vote results and views arrears and statistics |
| **Server** (`server/`) | System administrator (console) | server start/stop, connected clients (list, force disconnect), request history with CSV export |

## Architecture

```
 mobile (Expo)  ─┐
                 ├──  HTTP / JSON  ──►  server (console app)  ──►  database
 web (React)    ─┘
```

Both clients are written in TypeScript and share a common package, `shared/`, which contains the API client, the data types, formatting helpers, design tokens and the UI texts. Client code follows the MVVM pattern: views are React components, view models are hooks, and models are the types and API calls.

## Repository structure

```
qvorum/
├─ web/       React + Vite web app
├─ mobile/    React Native (Expo) mobile app
├─ shared/    TypeScript code used by both clients (@qvorum/shared)
├─ server/    server application
└─ docs/      requirements, UML diagrams, documentation
```

The UML diagrams are in `docs/Qvorum_UML_Diagrams.drawio` (open it with draw.io): the use case diagram (25 use cases) on the first page, then one activity diagram per use case. The file is generated by `docs/diagram-sources/generate.py` from `use_cases.py`, `activities.py` and `activities_admin.py`: change the data there and run `python docs/diagram-sources/generate.py`, because manual edits in draw.io are overwritten on the next run.

`web`, `mobile` and `shared` are npm workspaces, so all JavaScript dependencies are installed once from the repository root.

## Tech stack

- **Web:** React 19, TypeScript, Vite, Oxlint
- **Mobile:** React Native, Expo, Expo Router, TypeScript
- **Server:** Java, Spring Boot, Spring Data JPA (see [`server/README.md`](server/README.md))

## Getting started

### Prerequisites

- Node.js 22 or newer, and npm
- For the server: JDK 21 or newer and PostgreSQL (see [`server/README.md`](server/README.md))
- For the mobile app: an Android phone with [Expo Go](https://expo.dev/go), or an Android emulator

### Install

```bash
npm install
```

### Configure

Each application reads the server address from its own `.env` file. Copy the examples and adjust them:

```bash
cp web/.env.example web/.env
cp mobile/.env.example mobile/.env
cp server/.env.example server/.env
```

| Variable | File | Description |
| --- | --- | --- |
| `VITE_API_URL` | `web/.env` | server URL used by the web app |
| `EXPO_PUBLIC_API_URL` | `mobile/.env` | server URL used by the mobile app |
| `SERVER_HOST`, `SERVER_PORT` | `server/.env` | address and port the server listens on |

### Run

```bash
npm run web        # web app on http://localhost:5173
npm run mobile     # Expo dev server; scan the QR code with Expo Go
npm run typecheck  # type-check all TypeScript projects
```

## Running on separate machines

The server and the clients can run on different computers on the same network:

1. Start the server listening on `0.0.0.0` instead of `localhost`.
2. Find the server machine's local IP address (for example `192.168.1.10`).
3. Set `VITE_API_URL` and `EXPO_PUBLIC_API_URL` to `http://<that IP>:<port>`.

A phone can never reach the server through `localhost`, because on the phone `localhost` is the phone itself. If the network blocks traffic between devices, a phone hotspot or a tunnel such as ngrok works as an alternative.

## Future work

The course version keeps the scope focused. The extended design (33 use cases, in `docs/diagram-sources/portfolio/`) adds:

- personal activation codes and password reset by email
- several associations per administrator, several people per apartment (owners and tenants)
- push notifications on the phone
- consultations instead of votes, association documents, comments on issue reports, payment reminders
- recorded bank-transfer payments applied to the oldest unpaid month, repair and working-capital funds
- maintenance bill approval by the president, corrections after publishing, PDF exports
